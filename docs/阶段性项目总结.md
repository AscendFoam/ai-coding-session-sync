# AI Coding Session Sync 阶段性项目总结

> 更新时间：2026-04-29
>
> 本文用于阶段性回顾项目从立项到当前版本已经完成的工作、形成的设计决策、当前可用能力，以及接下来的推进重点。它和 [`工程化项目推进方案.md`](./工程化项目推进方案.md) 的关系是：前者偏“已经做了什么”，后者偏“接下来怎么做”。

## 1. 项目起点与问题定义

这个项目最初并不是从“做一个通用同步工具”的抽象命题开始，而是从一个非常具体、也非常真实的开发痛点开始：

- 同一个项目需要在多台设备之间切换开发；
- 一台设备上使用中转站提供的 Codex 额度，另一台设备上使用官方 Codex；
- 后续还希望把 Claude Code 也纳入同一套交接与同步体系；
- 设备、账号、provider、路径都可能不同，但仍然希望 AI 助手能快速“接上文”。

围绕这个问题，项目一开始先完成了需求澄清和方向判断：**不把“跨设备原样恢复原生会话”当作唯一目标，而是把“同步项目绑定的上下文包，并在另一端稳定完成交接”确立为主线。**

这一步非常关键，因为它决定了整个项目后面的架构方向：

- 不同步认证信息；
- 不押注某个 CLI 的私有内部格式；
- 先做 handoff-first，再逐步补 native/experimental 能力；
- 先把协议、可解释性、安全边界和跨设备可用性做扎实。

对应的早期研究和规划文档主要包括：

- [`docs/Codex会话同步方案.md`](./Codex会话同步方案.md)
- [`docs/工程化项目推进方案.md`](./工程化项目推进方案.md)
- [`docs/codex-adapter.md`](./codex-adapter.md)
- [`docs/claude-adapter.md`](./claude-adapter.md)

## 2. 第一阶段：从空项目到可运行的 CLI 骨架

项目最开始是一个空仓库，只有一份和 GPT 对话整理出来的方案文档。第一阶段的核心工作是把“想法”落成一个真正可运行的工程骨架。

这一阶段完成了以下内容：

- 建立 Python 项目结构与 `pyproject.toml`；
- 确立 CLI 命令名 `aiss`；
- 建立 `src/aiss/` 目录结构；
- 实现第一批命令入口与基础参数解析；
- 引入 `.ai-session-sync/` 作为项目本地同步状态目录；
- 约定 `manifests/`、`handoffs/`、`excerpts/`、`patches/`、`latest/` 等目录布局。

到这一阶段结束时，项目已经不再只是概念文档，而是一个具备基本命令面和目录初始化能力的工具原型。

当前 CLI 入口和主要命令实现位于：

- [`src/aiss/cli.py`](../src/aiss/cli.py)
- [`src/aiss/__main__.py`](../src/aiss/__main__.py)
- [`src/aiss/schema.py`](../src/aiss/schema.py)

## 3. 第二阶段：确立 handoff-first 协议与核心产物

在 CLI 骨架之后，项目优先完成了“导出什么”和“导入时靠什么接住上下文”的定义。

### 3.1 建立同步协议草案

项目定义了第一版同步协议草案，并把 snapshot 设计成不可变产物。核心产物包括：

- `manifest`：索引、项目状态、来源信息、工件路径；
- `handoff`：给人和模型都能读的交接文档；
- `excerpts`：最近高价值对话摘录；
- `patch`：可选的未提交工作补丁；
- `latest`：当前“最新快照”指针。

对应文档和 schema 已经落地：

- [`docs/protocol.md`](./protocol.md)
- [`docs/schemas/manifest.schema.json`](./schemas/manifest.schema.json)
- [`docs/schemas/inspect-output.schema.json`](./schemas/inspect-output.schema.json)
- [`docs/schemas/latest-pointer.schema.json`](./schemas/latest-pointer.schema.json)
- [`docs/schemas/ui-bundle.schema.json`](./schemas/ui-bundle.schema.json)

### 3.2 建立 handoff 生成能力

项目实现了 handoff 生成逻辑，并明确 handoff 内容不是简单的 transcript dump，而是围绕跨设备接力场景做结构化整理。当前 handoff 至少会覆盖：

- Current Goal
- Project State
- Completed Work
- Recent Context Summary
- Important Decisions
- Relevant Files
- Open Questions
- Next Steps
- Constraints
- Verification
- Notes

对应实现位于：

- [`src/aiss/handoff.py`](../src/aiss/handoff.py)

### 3.3 建立导入 prompt 生成能力

项目没有把“自动恢复到原生同一个 session”作为 MVP 前提，而是先把导入侧做成一个明确、可审查、可复制的 bootstrap prompt 流程。当前 `aiss import --print-prompt` 会：

- 读取 handoff；
- 读取 recent excerpts；
- 明确提醒另一端不要假设账号、provider、路径完全一致；
- 引导新的 AI 会话先复述当前状态、未完成事项和下一步计划。

这一步让项目从一开始就具备了跨账号、跨 provider 的稳定兜底路径。

## 4. 第三阶段：把 export 从手填信息推进到真实 transcript 抽取

这是项目从“样子像工具”变成“真的开始理解本地 AI 会话”的关键阶段。

### 4.1 Codex transcript 抽取适配器

项目实现了 Codex transcript 读取逻辑，支持：

- 检测 `AISS_CODEX_HOME` / `CODEX_HOME`；
- 默认回退到 `~/.codex`；
- 扫描 `sessions/**/*.jsonl`；
- 读取 `session_index.jsonl` 中的会话标题；
- 从 `session_meta` 和 `response_item` 中抽取用户/助手消息；
- 过滤无效内容和环境上下文噪音；
- 将绝对路径归一化为 `${PROJECT_ROOT}`；
- 将结果整理为统一的 `ExtractedContext`。

对应实现位于：

- [`src/aiss/adapters/codex.py`](../src/aiss/adapters/codex.py)

### 4.2 Claude Code transcript 抽取适配器

项目也同步实现了 Claude Code 适配器，支持：

- 检测 `AISS_CLAUDE_HOME`；
- 默认回退到 `~/.claude`；
- 扫描 `projects/**/*.jsonl`；
- 解析 JSONL transcript；
- 在必要时从 `history.jsonl` 做降级抽取；
- 归一化项目路径；
- 输出与 Codex 对齐的统一上下文结构。

对应实现位于：

- [`src/aiss/adapters/claude.py`](../src/aiss/adapters/claude.py)

### 4.3 上下文清洗、排序与目标提炼

项目没有停在“能读文件”这一层，而是继续把 adapter 做厚，补上了真正影响可用性的中间层逻辑：

- project path 匹配与 session ranking；
- 最近代表性窗口裁剪；
- 最新用户目标提炼；
- 用户/助手消息比例与数量统计；
- `score`、`score_reasons`、`goal_candidate` 等可解释字段；
- transcript 与 project root 的匹配优先级判断。

这一步的结果是：export 已经不只是把 `--goal` / `--notes` 写进文件，而是能真正从本地 transcript 中抽取“最近上下文”和“当前目标候选”。

### 4.4 `inspect` 调试视图

为了让这套抽取逻辑可观察、可调试、可前端化，项目又补了 `aiss inspect`，并逐步增强成现在这套调试能力：

- `--tool codex|claude`
- `--limit`
- `--all-excerpts`
- `--full`
- `--compare`
- `--json`

`inspect` 当前已经可以：

- 查看候选 session 排名；
- 查看被选中的代表性 excerpts；
- 查看完整 `all_excerpts`；
- 以 selected vs trimmed 的对照方式观察截窗效果；
- 输出带 compare metadata 的 JSON 结果，供前端或可视化直接消费。

## 5. 第四阶段：把 explainability 写进 manifest 和 inspect 契约

在 transcript 抽取稳定下来之后，项目做了一个非常对工程化有价值的决定：**不仅导出结果，还导出“为什么是这个结果”。**

当前 `manifest.source.contexts[]` 已经不只是简单记录来源路径，而是带上了：

- `session_id`
- `title`
- `updated_at`
- `transcript_path`
- `excerpt_count`
- `total_excerpt_count`
- `total_user_count`
- `total_assistant_count`
- `score`
- `score_reasons`
- `goal_candidate`

而 `inspect --json` 则进一步提供了：

- `all_excerpts[*].selected`
- `all_excerpts[*].selected_index`
- `excerpts[*].selected_index`
- `excerpts[*].all_excerpt_index`

这些字段一起构成了当前项目非常重要的一层能力：**会话选择和上下文截窗是可解释的，而不是黑箱。**

这件事后来也直接支撑了：

- schema 契约测试；
- Web UI 原型；
- 候选会话 explainability 视图；
- selected / all excerpts 双向跳转。

## 9. 第八阶段：建立 provenance 口径，区分契约字段与前端便利层

在 Web UI 原型和多文件模式逐步成型后，项目又做了一步很重要但容易被忽略的整理：把“哪些字段是后端契约，哪些是前端拼出来的便利层”明确文档化。

当前已经在文档中统一使用这三个词：

- `source-of-truth`
- `derived`
- `missing`

这套口径已经同步到：

- [`docs/protocol.md`](./protocol.md)
- [`docs/examples/public-sync-state/frontend-consumption.md`](./examples/public-sync-state/frontend-consumption.md)
- [`docs/examples/public-sync-state/README.md`](./examples/public-sync-state/README.md)

当前定义大意是：

- `source-of-truth`：直接来自协议产物或 fixture；
- `derived`：前端为了统一 bundle / split 视图而推导出来；
- `missing`：当前故意不提供，前端应显式感知其缺失。

这一步让前后端联调时更容易分清：

- “这是后端真实提供的数据”；
- “这是前端自己归一化出来的数据”；
- “这是当前协议还没给的数据”。

## 11. 第十阶段：latest pointer 冲突检测与选择流程

跨设备同步一旦落地，latest 指针冲突就成了绕不过去的实际问题。项目已经把这件事从隐性问题做成了显性流程。

当前已实现：

- latest pointer 冲突生成；
- `requires_selection` 状态；
- `candidates[]` 候选快照列表；
- `aiss latest show`；
- `aiss latest resolve --tool <tool> <snapshot_id>`；
- `import` 在冲突未解时拒绝继续，并给出下一步建议。

这一步让系统从“能同步文件”升级到“能处理并发设备各自导出所带来的语义冲突”。

## 13. 第十二阶段：补齐 patch export / inspect / apply 风险链路

这是目前项目里已经做得相当成体系的一条主线。

### 13.1 patch 导出

当前 `export --include-patch` 已经支持导出 Git patch，并把 patch 工件写入 snapshot。

### 13.2 patch 风险检查

当前 `import` 默认不会直接改动工作区，而是先做 patch 风险说明，包含：

- patch 文件是否存在；
- 当前目录是不是 Git worktree；
- export 时 branch / HEAD；
- 当前 branch / HEAD；
- worktree 是否 dirty；
- `git apply --check` 是否成功；
- `git apply --3way --check` 是否可行；
- 推荐的 replay 模式和命令。

### 13.3 patch 应用模式

当前已经实现三种 patch replay 策略：

- `apply`
- `3way`
- `branch`

并且具备这些安全边界：

- 默认 check-only；
- dirty worktree 默认拒绝；
- 需要 `--apply-patch` 才会发生变更；
- `--allow-dirty` 是显式逃生口；
- `branch` 模式会把高风险重放隔离到临时分支。

对应实现位于：

- [`src/aiss/patching.py`](../src/aiss/patching.py)

### 13.4 patch replay 可观测性

项目后续又进一步把 patch replay 建议喂给了：

- `status`
- `doctor`
- public fixtures
- UI bundle

当前 UI / fixture 层已经有 `patch_replay` 聚合字段，可直接表达：

- 当前 replay state；
- plain apply / 3way 能力；
- recommended mode；
- recommended reason；
- recommended command。

这意味着 patch replay 已经不再只是 CLI 内部逻辑，而是成了完整的协议与前端可消费状态。

## 17. 当前仍未完成或仍处于草案/早期状态的部分

虽然项目已经从空仓库走到了一个相当完整的 MVP+ 状态，但仍有一些关键部分尚未完成，或者只是完成了第一版。

主要包括：

- 还没有真正做原生 session resume / path remap；
- native mode 仍然只是规划方向，不是稳定能力；
- 远端 backend 目前以 Git sidecar 为主，尚未扩展到更多后端；
- 加密能力还没有落地；
- 生产级 redaction 策略还可以继续增强；
- Web UI 目前仍是静态原型页，不是正式应用；
- Claude adapter 还可以继续补 project memory / `CLAUDE.md` / richer profile；
- import 流程还没有和真实 Codex / Claude CLI 的自动注入动作打通。

换句话说，当前项目已经把“协议、CLI、同步、冲突、诊断、patch replay、fixture、前端原型”这几条主骨架搭起来了，但离完整产品仍然有下一阶段工作要做。

## 18. 这段时间最重要的阶段性成果

如果只挑最关键的阶段成果，我会认为有五件事尤其重要：

### 18.1 从“原样同步会话”转向“handoff-first”

这是整个项目最根本的方向修正。它让项目从一开始就更稳定、更安全，也更有跨 provider 的通用性。

### 18.4 patch replay 已经从提示升级到可执行策略

项目已经具备 patch 导出、风险检查、推荐模式和多种实际应用策略，而不仅仅是“把 diff 存起来”。
