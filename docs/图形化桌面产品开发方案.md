# AI Coding Session Sync 图形化桌面产品开发方案

> 更新时间：2026-04-29
>
> 本文基于当前 CLI、协议、synthetic fixture、Web UI 原型，以及你提出的桌面应用设想整理，目标是回答一个更具体的问题：**接下来如果要把项目推进成一个真正面向用户的图形化产品，应该怎么设计、怎么分层、怎么落地。**

## 1. 需求背景与目标

你现在想要的，不只是一个命令行同步工具，而是一个更完整的本地桌面应用。这个应用大致希望支持：

- 图形化展示 Codex 和 Claude Code 的所有本地会话；
- 按项目筛选会话；
- 查看会话详情与内容；
- 对会话做一些管理操作，比如修改会话名、修改会话绑定的项目路径；
- 手动同步到 GitHub 或其它云平台，也可以选择由应用自动同步；
- 对会话做备份；
- 在 Codex 和 Claude Code 之间做交接、传递，甚至某种“转换”。

这个设想是合理的，而且和当前项目方向并不冲突，但它也意味着项目要从“协议 + CLI 工具”进入“本地桌面产品”的新阶段。

这里最重要的不是马上决定用什么 UI 框架，而是先把产品边界定义清楚：

1. 哪些能力本质上是当前 CLI / 协议的自然延伸。
2. 哪些能力可以安全地通过 overlay 或辅助元数据实现。
3. 哪些能力如果直接改原生会话文件，风险很高，应该放进实验层或延后。

## 2. 对当前设想的总体判断

先给结论：

**你的设想是可行的，但不应该被实现成“直接图形化操作原生 Codex / Claude 会话文件”的工具，而应该实现成“本地会话工作台 + 协议化交接中心 + 可插拔同步中心”。**

换句话说，这个产品不应该把自己定位成：

- “Codex 官方会话管理器替代品”；
- “Claude Code 内部数据库编辑器”；
- “跨工具原生会话无损互转器”。

它更适合定位成：

**一个面向本地 AI coding session 的桌面工作台。它负责发现、索引、归档、解释、交接、同步和备份会话；必要时对原生会话做实验性增强，但默认不直接篡改原生状态。**

这个定位和当前项目已经积累出来的优势是高度一致的：

- 你已经有 handoff-first 协议；
- 已经有 Codex / Claude transcript 抽取 adapter；
- 已经有 explainability 字段；
- 已经有 sidecar sync；
- 已经有 latest conflict 与 patch replay 状态；
- 已经有前端 fixture 和原型页。

所以接下来不是推翻重来，而是**在现有“协议内核”之上增加一个 app 层和 GUI 层。**

## 3. 需求拆解：哪些需求可以直接承接，哪些需要重新设计

### 3.1 可以直接承接到现有项目结构的部分

这些功能和当前 CLI / 协议是顺着长出来的：

- 展示所有可识别的 Codex / Claude 本地会话；
- 按项目筛选；
- 显示会话标题、时间、tool、project、score、goal candidate；
- 查看 handoff、摘录、selected excerpts / all excerpts；
- 查看 patch replay 建议、latest conflict、doctor/status 诊断；
- 手动执行 export / pull / push / sync；
- 选择 sidecar backend 配置；
- 做 snapshot 级备份和恢复；
- 生成 Codex -> Claude 或 Claude -> Codex 的交接 prompt。

这些都可以在不破坏当前架构的前提下推进。

### 3.2 需要重新定义语义的部分

以下需求看起来直观，但如果直接实现，很容易踩到原生状态兼容性问题：

- “修改会话名”
- “修改会话绑定的项目路径”
- “把 Codex 会话转换成 Claude 会话”
- “把 Claude 会话转换成 Codex 会话”

这几件事如果理解成“去改对方原生 session/transcript 文件，让官方 CLI 也把它当成原生会话继续恢复”，风险非常高：

- 内部格式未必稳定；
- 一个字段未必足以表达“会话名”或“项目绑定”；
- 有些路径绑定可能分散在多个文件和缓存中；
- 直接改 native 数据会让后续 resume 变得不可预测；
- 跨工具 native conversion 几乎不可能稳定做到“像原生会话一样继续跑”。

因此这里必须换一种实现语义。

## 4. 核心产品策略：原生会话只读优先，用户编辑走 overlay

这会是整个桌面产品最关键的设计原则。

### 4.1 推荐默认策略

默认情况下：

- 原生 Codex / Claude 本地会话数据是**只读来源**；
- 图形化应用对会话的管理动作优先写入 **AISS overlay**；
- overlay 负责存储用户自定义的显示名、项目绑定修正、标签、备注、归档状态、同步偏好；
- 导出、同步、备份、转换优先基于“原生会话 + overlay + 规范化协议”生成结果。

### 4.2 这意味着什么

例如用户点“修改会话名”，默认不是真的去改 Codex 原生 session file，而是：

- 在 AISS 的 overlay 存一个 `display_name_override`；
- UI 上显示这个名字；
- handoff / export / bundle 中也优先使用这个名字；
- 原生文件仍然保持不动。

用户点“修改会话绑定的项目路径”，默认也不是直接改 transcript 中的 `cwd`，而是：

- 在 overlay 中建立 `project_binding_override` 或 path remap；
- AISS 之后在扫描、筛选、导出、同步时按这个 override 解释；
- 原生 transcript 保持原样。

### 4.3 为什么这很重要

因为这样可以同时满足三个目标：

1. 用户能获得“像会话管理器一样”的体验。
2. 工具不会因为去改原生内部格式而把 resume 弄坏。
3. 后续即使 Codex / Claude 升级了格式，AISS 的 GUI 管理层仍然大多可持续。

## 5. 建议的产品定位

我建议把图形化产品定位成：

**AISS Desktop：一个本地优先的 AI coding session 工作台。**

它有四条主线能力：

### 5.1 Session Explorer

统一发现和展示 Codex / Claude Code 的本地会话。

### 5.2 Project Workspace

把会话按项目归类，展示项目相关的上下文、handoff、patch、sync 状态、latest 冲突与候选。

### 5.3 Sync Center

让用户用图形化方式配置 sidecar backend，执行手动同步，查看历史、冲突和风险。

### 5.4 Transfer / Backup Center

做 snapshot 导出、会话归档、跨工具交接、备份和恢复。

这个定位比“桌面版 CLI”更高一层，也比“原生会话编辑器”更稳。

## 6. 产品信息架构

建议把应用拆成 6 个一级视图。

## 6.1 首页 Dashboard

展示：

- 最近活动项目；
- 最近活动会话；
- 待处理 latest conflict；
- 可导入的 patch replay 建议；
- 最近同步状态；
- 备份状态与风险提醒。

这是“打开 app 先看整体状态”的入口。

## 6.2 Session Library

这是“所有会话总览”页。

建议支持：

- 按工具筛选：Codex / Claude / All；
- 按项目筛选；
- 按设备来源筛选；
- 按状态筛选：active / archived / synced / conflict / dirty / warning；
- 搜索标题、notes、goal candidate、路径。

列表字段建议至少包括：

- display name
- 原生标题
- tool
- project
- updated_at
- excerpt count
- score
- goal candidate
- dirty / patch / conflict 徽标
- sync status

## 6.3 Session Detail

这是最核心的详情页。

建议分成几个 tab：

- `Overview`
- `Transcript`
- `Excerpts`
- `Handoff`
- `Patch`
- `Sync`
- `Metadata`

### Overview

展示：

- 会话标题与 overlay 名称；
- tool / session id / transcript path；
- 关联项目；
- goal candidate；
- score 与 score reasons；
- recent selected excerpts 摘要；
- latest sync state。

### Transcript

展示：

- 原始清洗后的对话流；
- 搜索；
- 按 user / assistant 过滤；
- large output 折叠；
- 敏感内容标记。

### Excerpts

复用你现在已经有的 compare 设计：

- 左侧 selected excerpts
- 右侧 all excerpts
- selected / trimmed 对照
- selected_index / all_excerpt_index 跳转

### Handoff

展示：

- 当前 snapshot 的 handoff markdown；
- 可切换 Codex / Claude import prompt 模板；
- 可复制 / 导出。

### Patch

展示：

- patch 是否存在；
- plain apply / 3way / branch 建议；
- current checkout 风险；
- 导入前推荐命令。

### Sync

展示：

- latest pointer；
- latest conflict 候选；
- sidecar backend；
- 最近 push / pull / sync 记录；
- snapshot 历史。

### Metadata

展示和编辑：

- display name override
- project binding override
- tags
- notes
- archive flag
- sync policy

## 6.4 Project View

这是“按项目看会话”的视图。

建议展示：

- 项目标识；
- Git remote / branch / head；
- 该项目下所有相关会话；
- 当前推荐 session；
- 当前 latest snapshot；
- dirty / patch / conflict 状态；
- 可直接执行 export / import / sync。

这里会成为“这个项目现在交接到哪一步了”的总控台。

## 6.5 Sync Center

这里是同步后端和操作入口。

建议支持：

- 配置 Git remote；
- 选择 GitHub / Gitee / GitLab / self-hosted Git / local folder；
- 配置 branch；
- 选择手动同步还是自动同步；
- 查看最近同步历史；
- 查看失败原因；
- 手动 resolve latest conflict。

注意：

这里的“GitHub / Gitee / GitLab 支持”初期其实不需要做平台 API 集成，**只需要把它们当成 Git remote** 即可。平台差异先不要做重。

## 6.6 Backup / Transfer Center

这里负责两类动作：

### Backup

- 导出 snapshot 包；
- 导出 raw native transcript copy；
- 导出 bundle zip；
- 恢复某个历史 snapshot；
- 标记 public-safe / private / encrypted。

### Transfer

- Codex -> Claude handoff
- Claude -> Codex handoff
- same-tool handoff
- snapshot bundle export

注意这里建议用词是：

- `handoff`
- `transfer`
- `bootstrap`

而不是一开始就承诺：

- `native conversion`
- `lossless conversion`

因为后者很容易过度承诺。

## 7. 数据模型建议

当前项目是 project-bound 的，而你现在要的 GUI 还需要“全局浏览所有会话”。这意味着我们要新增一层 **app-level catalog**。

### 7.1 保留现有 project-bound sync state

现有：

- `.ai-session-sync/`

继续保留，它是每个项目的同步状态根。

### 7.2 新增 app-level catalog

桌面应用需要一个全局本地状态目录，建议放在用户数据目录中：

- macOS: `~/Library/Application Support/aiss/`
- Windows: `%AppData%/AISS/`
- Linux: `~/.local/share/aiss/`

这里建议存：

- 扫描索引缓存；
- 会话 overlay；
- 项目绑定映射；
- backend profile；
- sync history；
- backup history；
- local app settings。

### 7.3 核心实体

建议定义以下实体：

#### NativeSession

表示原生扫描出来的只读会话。

字段示例：

- `tool`
- `native_session_id`
- `transcript_path`
- `native_title`
- `native_project_path`
- `updated_at`
- `message_count`
- `raw_fingerprint`

#### SessionOverlay

表示 AISS 自己的附加管理层。

字段示例：

- `session_key`
- `display_name_override`
- `project_binding_override`
- `tags`
- `notes`
- `archived`
- `sync_policy`
- `preferred_backend_profile`
- `last_reviewed_at`

#### ProjectRecord

表示 AISS 识别出来的项目。

字段示例：

- `project_id`
- `display_name`
- `root_candidates`
- `git_remote`
- `path_aliases`
- `tool_preferences`

#### SyncProfile

表示一个同步后端配置。

字段示例：

- `profile_id`
- `kind` (`git`, `local-folder`, `webdav`, `s3` future)
- `remote_url`
- `branch`
- `auth_mode`
- `auto_sync_enabled`

#### TransferJob

表示一次手动交接/转换操作。

字段示例：

- `source_tool`
- `target_tool`
- `source_session_key`
- `snapshot_id`
- `mode` (`handoff`, `bundle`, `native-experimental`)
- `created_at`

## 8. “修改会话名”和“修改项目绑定”的正确实现方式

这两项是需求里最容易误伤系统稳定性的地方，所以单独说。

## 8.1 修改会话名：分三层能力

### Level 1：Overlay Rename

推荐默认方案。

- 改的是 AISS 中显示给用户看的名字；
- 不改原生文件；
- 所有导出、handoff、UI、sync 记录优先使用这个名字。

这是应该最先落地的。

### Level 2：Export Title Override

作为 export 产物层的增强：

- snapshot / handoff title 使用 override；
- 不要求底层 native state 改名。

### Level 3：Native Rename

实验功能，默认关闭。

- 尝试改 native metadata；
- 需要显式确认；
- 必须标注“不保证官方 CLI 继续按原方式恢复”。

我不建议在前几个 milestone 做。

## 8.2 修改会话绑定项目路径：也分三层能力

### Level 1：Project Rebind Overlay

推荐默认方案。

- 用户选择“这个 session 应该归到哪个项目”；
- AISS 后续按这个 override 归类和导出；
- 不改原始 transcript。

### Level 2：Path Remap Rule

适用于跨设备路径变化：

- 建立 `/Users/.../repo` -> `D:/.../repo` 这种映射；
- 影响 import prompt、project match、handoff render；
- 仍不改 native transcript。

### Level 3：Native Path Rewrite

实验功能，默认关闭。

这属于很危险的能力，因为很多工具对 path 的依赖可能不止一个字段，甚至不止一个文件。

我的建议是：

**桌面版产品先把“重绑项目”和“路径映射”作为 AISS 解释层能力，而不是 native 改写能力。**

## 9. “Codex 和 Claude 会话互转”应该怎么定义

这是另一个非常容易被误解的点。

### 9.1 不建议一开始承诺 native-to-native conversion

不建议把第一版目标定义成：

- “把 Codex session 转成 Claude 原生 session”
- “把 Claude session 转成 Codex 原生 session”

因为这几乎一定不稳定，而且长期维护成本很高。

### 9.2 建议先做 protocol-level transfer

也就是：

`native session -> normalized context -> handoff bundle -> target-tool bootstrap prompt`

这条链路当前项目已经有很大一部分基础了。

第一版可以做：

- `Codex -> Claude handoff`
- `Claude -> Codex handoff`
- `Codex -> Codex handoff`
- `Claude -> Claude handoff`

区别主要在于：

- prompt 模板不同；
- tool-specific note 不同；
- excerpt 选取权重可不同；
- project memory / CLAUDE.md / Codex-specific hints 的拼接策略不同。

### 9.3 后续可以做 experimental native assist

之后可以做实验层功能：

- 导出 native transcript copy；
- 生成目标工具可消费的参考文件；
- 尝试半自动创建目标工具“新会话初始化草稿”；
- 但不要承诺它就是目标工具的“原生恢复态”。

## 10. 同步策略建议

你已经明确说了：“一般是手动同步。” 这个判断我非常赞同。

### 10.1 默认策略：Manual First

GUI 默认应当：

- 手动 export；
- 手动 pull；
- 手动 push；
- 手动 resolve conflict；
- 手动 apply patch；
- 手动触发 transfer / backup。

原因很简单：

- 会话数据可能敏感；
- patch replay 风险不低；
- latest conflict 不是纯技术问题，有时是决策问题；
- 用户更愿意先掌控。

### 10.2 可选策略：Guided Auto Sync

自动同步不是不能做，但应该是 opt-in。

建议分三档：

#### Auto Mode A：Prompted Auto

- 检测到新 snapshot 后弹出建议；
- 用户点确认才 push。

#### Auto Mode B：Scheduled Auto

- 每隔 N 分钟同步；
- 只同步 handoff bundle，不自动 apply patch。

#### Auto Mode C：Project Policy Auto

- 某个项目单独开启；
- 只对私有 sidecar backend 生效；
- 允许配置“只在 clean worktree”时自动同步。

### 10.3 其它云平台支持方式

初期建议按三层推进：

#### Layer 1：Generic Git Remote

支持：

- GitHub
- Gitee
- GitLab
- Forgejo
- 自建 bare repo

都通过 `remote URL + branch` 处理。

#### Layer 2：Local Folder / Shared Drive

支持：

- 本地文件夹
- NAS
- iCloud / OneDrive / Dropbox 同步目录

这类其实对很多用户反而更实用。

#### Layer 3：对象存储 / WebDAV / 云存储连接器

后续再做：

- S3 / R2 / GCS
- WebDAV
- 自定义 connector

## 11. 技术架构建议

## 11.1 不建议直接把当前 CLI 粗暴塞进桌面壳

当前 CLI 已经很有价值，但 GUI 产品如果只是按钮去 shell out 执行命令，会有几个问题：

- 状态回传不够细；
- 长任务与取消、进度条不好做；
- 会话列表、筛选、搜索需要更稳定的结构化 API；
- overlay 编辑不适合一直走命令行参数。

所以需要在现有 CLI 和 GUI 之间再加一层 **App Service API**。

## 11.2 推荐分层

建议最终形成 4 层结构：

```text
Native session files
        ↓
Adapter / Normalization Layer
        ↓
AISS Core + App Service API
        ↓
Web UI / Desktop Shell
```

### Layer 1：Native adapters

继续负责：

- 扫描本地 Codex / Claude 会话；
- 解析 transcript；
- 生成统一上下文对象。

### Layer 2：AISS Core

负责：

- project identity
- overlay merge
- export / import
- sync orchestration
- latest conflict
- patch replay inspection
- backup / transfer jobs

这层应尽量保持 Python 为主，因为当前核心已经在这里。

### Layer 3：App Service API

这是新增的一层。

建议职责：

- 给前端提供结构化 JSON API；
- 维护扫描缓存；
- 维护 overlay CRUD；
- 提供任务进度、日志、失败原因；
- 统一调用现有 core 能力。

推荐接口风格：

- `GET /sessions`
- `GET /sessions/{id}`
- `PATCH /sessions/{id}/overlay`
- `GET /projects`
- `POST /exports`
- `POST /imports`
- `POST /sync/pull`
- `POST /sync/push`
- `POST /sync/resolve-latest`
- `POST /transfers`
- `POST /backups`

### Layer 4：UI 层

负责：

- 会话浏览；
- 详情展示；
- 表单编辑；
- 冲突选择；
- patch replay 引导；
- backend 配置；
- backup / transfer 操作。

## 11.3 桌面框架选择建议

这里我建议不要一上来执着于“Windows exe 还是 mac app”，而应该先选一个**能最大化复用现有成果**的实现路径。

### 方案 A：本地 Web App + 后续桌面壳

技术形态：

- Python App Service
- React / TypeScript 前端
- 开发期先跑本地 Web UI
- 后期再用 Tauri 或 Electron 打包

优点：

- 最能复用你已经有的 `conflict-prototype.html` 和 fixture；
- 前端开发效率高；
- 协议联调最顺；
- 不会过早被桌面打包问题拖住。

缺点：

- 需要前后端分层；
- 桌面打包是第二步。

### 方案 B：Tauri + Web 前端 + Python sidecar

技术形态：

- Web UI
- Tauri 桌面壳
- Python 作为 sidecar 服务

优点：

- 安装包更轻；
- 跨平台桌面体验更好；
- 能复用 Web UI。

缺点：

- 打包 Python sidecar 有一定复杂度；
- Rust + Web + Python 三栈协同更复杂。

### 方案 C：PySide6 / Qt

技术形态：

- 全 Python
- Qt 原生桌面 UI

优点：

- 单语言；
- Python core 调用非常直接；
- 本地桌面打包路径清晰。

缺点：

- 几乎不能复用当前 Web 原型与前端 fixture 工作流；
- UI 开发节奏和 Web 不同；
- 以后做 Web 版会重复建设。

### 推荐结论

我建议：

**第一阶段先做 “Python App Service + 正式前端 Web UI”，第二阶段再套 Tauri 桌面壳。**

这是和当前项目积累最对齐、风险最低、复用率最高的路径。

## 12. 代码结构演进建议

建议后续把仓库逐步演进成这样的形态：

```text
src/aiss/
  adapters/
  backends/
  core/
  api/
  desktop/

apps/
  web/
  desktop/

docs/
  examples/
  schemas/
```

其中：

- `src/aiss/` 继续做核心能力；
- `src/aiss/api/` 新增本地服务层；
- `apps/web/` 放正式前端；
- `apps/desktop/` 放 Tauri 或其它桌面壳。

这样当前 CLI 不会被废掉，而是变成 core 的一个入口。

## 13. 推荐的功能分期

这里我建议按 6 个 milestone 推。

## Milestone 0：产品边界与数据层定稿

目标：

- 明确 overlay 模型；
- 明确 app-level catalog；
- 明确 session / project / backend / transfer / backup 数据结构；
- 明确哪些字段是 source-of-truth，哪些是 derived；
- 明确哪些操作默认只改 overlay。

产出：

- 产品方案文档；
- API 草案；
- overlay schema 草案；
- session catalog schema 草案。

## Milestone 1：只读版 Session Explorer

目标：

- 图形化展示 Codex / Claude 所有会话；
- 支持项目筛选、搜索、排序；
- 支持 session detail；
- 支持 excerpts compare view；
- 支持 handoff / patch / sync 状态展示。

这一阶段不做“改名”“改绑”“同步写操作”。

产出：

- 正式前端工程；
- 本地 API；
- 第一版会话列表与详情页。

## Milestone 2：Overlay 编辑层

目标：

- 支持 display name override；
- 支持 project rebind；
- 支持 tags / notes / archive；
- 支持 path remap rules；
- UI 中明确区分 native data 和 overlay data。

这一阶段是让产品真正具备“管理器”味道的关键。

## Milestone 3：Sync Center

目标：

- 图形化配置 backend；
- 手动 pull / push / sync；
- latest conflict 选择；
- status / doctor 面板；
- patch replay 建议与导入引导。

这一阶段可以直接承接你现在 CLI 的大量能力。

## Milestone 4：Backup / Transfer Center

目标：

- 导出 snapshot bundle；
- 管理历史快照；
- Codex <-> Claude handoff transfer；
- public-safe export；
- backup / restore。

这一阶段会让产品从“会话查看器”升级成“真正的交接工作台”。

## Milestone 5：桌面壳与安装包

目标：

- 打包 Windows exe / installer；
- 打包 mac app；
- 系统托盘或菜单栏；
- 打开本地项目；
- 本地文件选择；
- 本地通知。

这一阶段再处理“像一个真正 app”那层体验。

## Milestone 6：实验功能层

目标：

- native rename 实验开关；
- native path rewrite 实验开关；
- native resume assist；
- 受限自动同步；
- 加密后端。

这一阶段必须明确标注“实验功能”和风险提示。

## 14. 当前阶段最适合先做的事情

如果只谈“下一步最合理的一小段”，我会建议先做这 4 件事：

### 14.1 先定义 app-level schema

当前你已经有：

- manifest schema
- inspect schema
- latest schema
- ui bundle schema

接下来最应该补的是：

- `session-catalog.schema.json`
- `session-overlay.schema.json`
- `project-record.schema.json`
- `sync-profile.schema.json`

这是 GUI 产品真正起步的地基。

### 14.2 把现有 CLI core 包一层 App API

先别急着上桌面壳。

先做：

- 本地 JSON API；
- `/sessions`、`/projects`、`/sync`、`/transfers` 的结构化接口；
- live data 能映射到前端，而不是只靠 synthetic fixture。

### 14.3 把当前原型页升级成正式前端骨架

你现在已经有很好的 UI seed：

- fixture
- bundle / split 双路径
- provenance 口径
- patch replay 面板
- conflict / dirty 演示

最自然的推进方式，是把它升级成真正的前端项目，而不是另起炉灶。

### 14.4 把 overlay 模型落地

在 GUI 阶段，overlay 会是最重要的新数据层。

建议优先落地两个字段：

- `display_name_override`
- `project_binding_override`

因为这两项最能直接回应你的产品设想。

## 15. 主要风险与提前规避建议

## 15.1 最大风险：把 GUI 做成 native file editor

如果一开始就直接改 Codex / Claude 的原生状态文件，短期看很爽，长期几乎一定痛苦。

规避方式：

- 默认只读 native；
- 默认写 overlay；
- native mutation 只放实验层。

## 15.2 第二风险：桌面壳选型过早

如果一开始就陷入 exe / dmg / 签名 / 打包细节，产品核心能力反而会变慢。

规避方式：

- 先做本地 Web UI；
- 后做桌面打包。

## 15.3 第三风险：把“跨工具交接”误做成“原生互转”

用户真正需要的通常不是“字节级无损转换”，而是“另一边的 AI 能顺畅接上工作”。

规避方式：

- 先做 handoff-level transfer；
- 明确文案不要过度承诺 native conversion。

## 15.4 第四风险：全局会话浏览与项目绑定打架

当前项目是 project-bound，而 GUI 又需要 global view。

规避方式：

- 明确分离 app-level catalog 和 project-bound sync state；
- 不把所有全局状态塞回 `.ai-session-sync/`。

## 16. 建议的产品结论

综合你的设想和当前项目基础，我建议接下来的图形化产品路线可以总结成一句话：

**先把 AI Coding Session Sync 做成一个“本地会话工作台”，而不是“原生会话编辑器”。**

更具体一点：

- 会话浏览、筛选、详情、handoff、patch、sync、backup、transfer，这些都应该尽快做；
- 会话改名、项目改绑，先做 overlay；
- GitHub / Gitee / GitLab 先统一抽象成 Git remote；
- 自动同步默认不开；
- Codex / Claude 之间先做 handoff-level transfer，不承诺原生互转；
- 架构上先做 App Service + 正式前端，再打包桌面壳。

如果按这个方向推进，这个项目会从“CLI + 协议工具”自然长成一个真正可用的桌面产品，而且不会因为过早碰原生内部状态而把自己拖进高维护泥潭。
